# Xec — аудит, стратегия и план приведения к индустриальному уровню

Дата аудита: 2026-08-03. Базовая версия: 0.9.0.
Объём анализа: 232 исходных файла / ~70 500 LOC в 6 пакетах + сайт.

---

## 1. Вердикт

**Идея проекта подтверждена рынком и уникальна. Реализация — нет.**

Исследование конкурентов (npm/GitHub API, 2026-08-03) показало: **ни один инструмент в экосистеме
JS/TS не объединяет local + SSH + Docker + Kubernetes под одним template-literal API.** zx (45.6k
звёзд, 2M загрузок/нед), execa (157M загрузок/нед), dax, Bun Shell — все заканчиваются на локальной
машине. Команды, которым нужно удалённое исполнение, вручную склеивают `execa` + `ssh2` (10.7M/нед)
+ `dockerode` (6.5M/нед) + `@kubernetes/client-node` (2.6M/нед). Именно этот шов закрывает xec.

Но реализация сегодня **не выдерживает собственных заявленных стандартов** и не готова к
продакшену в том виде, в каком заявлена. Ключевое:

| Заявление в CLAUDE.md | Реальность |
|---|---|
| «ZERO external dependencies» в core | На момент аудита 4 зависимости: `js-yaml`, `shell-escape`, `ssh2`, `zod`, причём `shell-escape` не импортировался нигде (удалён) |
| «100% Type Safety, no `any`» | 134 явных `any` только в `ops`; десятки в core/CLI |
| «No Silent Failures» | Найдено ≥6 фич, которые **молча делают ничего и рапортуют успех** |
| «100% Coverage Required» | ~9 538 LOC конфиг-системы — 0 тестов; 24 тест-файла CLI импортируют удалённые пути |
| «Security first» | 5 подтверждённых векторов инъекции команд, утечки паролей в ошибки |

Главная проблема не в количестве багов, а в их **классе**: система, исполняющая команды на
продакшен-инфраструктуре, содержит фичи, которые сообщают об успехе, ничего не выполнив. Это
опаснее падения.

## 2. Стратегия и позиционирование

### 2.1. Текущее состояние дистрибуции

- `@xec-sh/core` — **6 загрузок/нед**, `@xec-sh/cli` — **2 загрузки/нед**
- GitHub `xec-sh/xec` — **6 звёзд, 0 issues**, последний публичный push 2026-03-15
- Документация хорошо проиндексирована Google, но приводит на проект, который выглядит заброшенным

Фактически проект имеет нулевое внешнее доверие. Это меняет приоритеты: **сначала честность
и надёжность, потом объём фич.** Заявления уровня «high-reliability system» при 6 звёздах
работают против проекта, если код им не соответствует — их проверят.

### 2.2. Рекомендуемое позиционирование

> **Xec — слой исполнения для TypeScript-инфраструктуры.** Тот же `$`, что и в zx, но выполняется
> где угодно: локальная оболочка, SSH-парк, Docker-контейнеры, поды Kubernetes — с пулингом
> соединений, типизированными результатами и декларативным CLI из targets/tasks. Там, где zx
> заканчивается на ноутбуке, а Ansible требует Python и YAML, xec даёт TypeScript-командам
> (и их AI-агентам) один безопасный способ исполнять команды во всех средах.

**Слоган:** `One $ for every environment.`
Альтернативы: `Run anywhere. Type everything.` / `From laptop to cluster, same line of code.`

### 2.3. Три ниши по приоритету

1. **Execution substrate для AI-агентов** (окно открыто сейчас). Агентам нужно типобезопасное,
   аудируемое, защищённое от инъекций исполнение в разных средах. Существующие MCP-серверы для SSH
   — фрагментированные однохостовые обёртки. У xec уже есть маскирование секретов, лимиты, пулинг —
   официальный MCP-сервер поверх xec — самый дешёвый захват этой ниши. Риск: окно закроется за ~12 месяцев.
2. **CI/CD и деплой-скриптинг без клея.** Между «zx-скриптом» и «полноценным Pulumi/Terraform»
   сейчас пусто.
3. **Fleet/homelab-операции для TS-команд.** Ansible/pyinfra — Python, kamal — Ruby. TS-ответа нет.

**Чего НЕ делать:** не конкурировать в локальном исполнении. Оно коммодитизировано Bun Shell,
zx и execa. Любое позиционирование вокруг локального DX проиграно заранее.

### 2.4. Главные стратегические риски

1. Локальное исполнение коммодитизировано — вести нужно удалённым/унифицированным.
2. Дефицит доверия: 6 загрузок/нед против брендов Google и sindresorhus.
3. Мёртвое публичное присутствие: ритм публикаций — это тоже маркетинг.
4. Матрица поддержки: 6 пакетов × 4 адаптера × 3 рантайма при планке execa (релиз/нед, 1 open issue).
5. Ниша AI-агентов может закрыться MCP-native инструментами.

### 3.2.1. Свидетельство реального потребителя (omnitron)

Omnitron — 49 файлов, использующих `@xec-sh/*`. Что показал разбор:

- **`$` — флагманский API — не используется ни разу.** Команды всегда приходят строкой из конфига
  или БД, а `$` требует tagged template. Обходятся через `engine.raw([command] as any)`.
- **`engine.run()` задокументирован в их коде как сломанный** (`execution.service.ts:112`):
  «engine.run() interpolates options into the command string which corrupts it».
  **Воспроизведено:** `$.run('echo hello', {cwd:'/tmp'})` → команда `e'{"cwd":"/tmp"}'cho hello`.
  Метод итерирует строку **посимвольно**, вставляя опции между символами. **ИСПРАВЛЕНО** —
  теперь бросает `TypeError` с указанием рабочих альтернатив.
- **Docker-адаптер «может зависать»** — два места сознательно обходят его ради
  `execFile('docker', …)` (`container-runtime.ts:198`, `infrastructure.service.ts:555`).
- **Всё, что типизировано в xec, деградирует до `any`** у потребителя — при том, что проект
  в остальном строго типизирован.
- **~2 690 строк обёрток**, и у каждой — полный запасной путь без xec: зависимость трактуется
  как опциональная в рантайме. Это самый громкий сигнал о недоверии к API.
- Конфиг-система, `.xec/`, tasks, targets — **0 использования**.

Вывод для стратегии: главная ценность 1.0 для существующего потребителя — не новые фичи,
а стабильный типизированный API, позволяющий удалить половину этих 2 700 строк.

## 4. Архитектурные дефекты

### 4.1. Дублирование и разрастание CLI

- `in.ts` ↔ `on.ts` — **~129 идентичных строк** (53 блока). `executeTask()` существует в трёх
  расходящихся копиях, `executeParallel()` — в трёх **разных алгоритмах** для одной задачи.
- `runInteractiveMode()` — 7 независимых реализаций.
- Zod-схема с хвостом `profile/verbose/quiet/dryRun` скопирована дословно в 7 файлов.
- `tasks.ts` (332 LOC) **полностью мёртв**: не зарегистрирован, ноль импортов. При этом
  `run.ts:266` советует пользователю «Run `xec tasks`» — команды не существует.
- `new.ts` — 2 424 LOC, из них ~850 — строковые шаблоны исходников.

### 4.2. Несогласованность UX

- **Четыре механизма вывода**: глобальный `-o/--output`, `--format` в `inspect`, `--json` в
  `logs`/`config`, `-f/--format` в `secrets`.
- **`-f` означает пять разных вещей**: `--force`, `--follow`, `--filter`, `--file`, `--format` —
  причём в одном дереве `secrets` это одновременно `--force` и `--format`.
- **Пять синтаксисов таргета**: `on <hosts>`, `in containers.x`, `copy target:path`,
  `logs [target] [path]`, `forward <target> <port-mapping>`.
- Рекламируемые флаги, кидающие «not implemented»: `--aggregate` в `logs`, `-r/--reverse` в `forward`.
- 62 вызова `process.exit()` в обход `handleError`; 78 голых `throw new Error()`.
- `throw new Error('cancelled')` как поток управления, ловится через `message.includes('cancelled')` —
  любая настоящая ошибка со словом «cancelled» проглатывается как отмена пользователем.

### 4.3. Разрастание core за пределы своей задачи

`docker-fluent-api/services/*` — **~2 500 LOC пресетов в стиле testcontainers** внутри движка
исполнения команд: `redis.ts` (906), `messaging.ts` (641), `databases.ts` (553), `ssh.ts` (423).
Качество: жёстко зашитые порты (два Kafka не сосуществуют), несуществующий тег
`redis/redis-stack:alpine`, путь `undefined-zk`, вызовы `rabbitmqadmin`, которого нет в образе,
дефолтные креды `user/password`. Покрытие — только проверки конфиг-объектов; ни один `start()`
или `exec()` не выполняется в тестах, поэтому дефект №9 и выжил.

### 4.4. Реальность тестов

- **Ложные тесты**: `test/unit/utils/audit-logger.test.ts` — 7 строк, `describe.skip` с заглушкой.
- **Битый бенчмарк**: `test/performance/masking-benchmark.ts` импортирует несуществующий
  `masking-optimizer.js`; файл не `.test.ts`, поэтому vitest его не собирает и не падает.
- **Молчаливый no-op**: `docker/redis-cluster.test.ts` выходит из `beforeAll` при отсутствии
  Docker — тесты зеленеют, ничего не проверив.
- **Мёртвый набор CLI — хуже, чем казалось.** Замер на живом прогоне: **40 из 44 тест-файлов
  `apps/xec` падают** (69 упавших тестов), потому что импортируют `../../src/{config,secrets,api,
  utils}/…` — всё это переехало в `packages/ops` и в `apps/xec/src` больше не существует. Каждый
  сломанный импорт разрешается в существующий модуль `packages/ops/src`, то есть покрытие
  восстановимо переносом, а не переписыванием. Причём эти тесты покрывают больше модулей
  (`target-resolver`, `task-manager`, `crypto`, `machine-id`, `api/*`), чем есть в `ops` сейчас.
- Флаги `XECSH_TEST_SSH`/`_DOCKER`/`_K8S` из CLAUDE.md **не существуют** в коде.
- Полностью без покрытия: `process-context.ts` (488), `docker-api.ts` (329), `suggestions.ts` (322),
  `interactive.ts` (263), `ssh-api.ts` (205), `kubernetes-utils.ts` (175), 90% `transfer.ts`.

### 4.5. Документация против кода

- `api/index.md:208` документирует `createSSHPool` — **функции не существует**.
- ~~`execution-engine/overview.md:32` — `.pod()` не существует~~ — **находка ошибочна, снята.**
  Проверено чтением кода (`kubernetes-api.ts:109,315`) и вызовом в рантайме:

- Три взаимно противоречащих описания приоритета конфигурации в трёх файлах.
- `website/docs/ops/*` (9 файлов) не подключены к `sidebars.ts` — недостижимы.

## 8. Повторный независимый аудит (2026-08-04)

Проведён второй заход с требованием проверять эмпирически. Ниже — то, что
нашлось **после** первого раунда исправлений, то есть новые дефекты.

### 8.1. Библиотека захватывала процесс потребителя (критично)

Импорт `@xec-sh/core` устанавливал **четыре process-глобальных обработчика**,
три из которых вызывали `process.exit()`. Обработчик `unhandledRejection`
срабатывал на отказах **самого приложения-хоста**, не связанных с xec.

Воспроизведено: программа, которая импортирует xec и затем имеет собственный
отвергнутый промис, убивается своей же зависимостью — с диагностикой от xec.
Для библиотеки, на которой предлагается строить инструменты, это дефект
не по степени, а по сути.

Скрывающий фактор — тот же, что и у санитизации ошибок в первом раунде:
обработчики не ставились при `NODE_ENV=test`, поэтому **ни один тест не мог
это увидеть**. Новые тесты работают в дочерних процессах именно поэтому.

**ИСПРАВЛЕНО**: импорт больше не ставит ни одного обработчика; очистка
доступна явным `installCleanupHandlers()`, который вызывает CLI — он-то
процессом владеет правомерно. Сигнальные обработчики больше не решают за
хост, когда ему завершаться.

### 8.2. Заявление о кроссплатформенности было неверным

Шесть реэкспортов типов записаны как реэкспорты значений
(`export { ExecutionResult } from …` вместо `export type { … }`). `tsc` их
вычёркивает, но **любой загрузчик со стиранием типов** трактует их как
рантайм-импорты.

Следствие: `import '@xec-sh/core'` падал под tsx, под нативной поддержкой TS
в Node и под Bun. То есть заявленная в CLAUDE.md работа «одинаково на Node,
Bun и Deno» не выполнялась ни в одном из этих случаев.

**ИСПРАВЛЕНО**. Проверено: пакет загружается под Bun 1.3.11, где ранее падал.
Остальные четыре пакета проверены тем же способом — у них проблемы нет.

### 8.3. Пакет нельзя было импортировать по имени

`@xec-sh/core` — единственный пакет без поля `exports`. Node без него не
резолвит self-reference, поэтому **все 35 примеров** в `packages/core/examples`,
каждый из которых импортирует `@xec-sh/core` (как это сделал бы пользователь),
падали с `ERR_MODULE_NOT_FOUND`. Неработающая документация.

**ИСПРАВЛЕНО**, проверено запуском примера.

### 8.4. Сайт выглядел как учебный проект

Причина конкретна: `--ifm-font-family-base` был задан как `'Fira Code',
monospace` — весь сайт, включая заголовки и абзацы, набирался моноширинным.
Поверх этого — градиент во весь экран, четыре стоковые иконки и код-блок
с низким контрастом поверх градиента: демонстрация продукта была наименее
читаемым элементом страницы.

**ПЕРЕДЕЛАНО**: проза в Inter, моноширинный только в коде; терминальное окно
с подсветкой как центр первого экрана; сдержанные слои вместо градиента;
секция «какой шов это закрывает» с четырьмя библиотеками, которые иначе
собирают вручную.

### 8.5. Линтер и типизация

- Сайт **вообще не покрывался** линтером: штатный скрипт охватывал только
  `apps/` и `packages/`. Добавлен.
- `website/tsconfig.json` ссылался на необъявленный тип-пакет, из-за чего
  `tsc --noEmit` падал на каждом запуске — предсуществующая ошибка, делавшая
  проверку типов сайта бесполезной. Исправлено; проверено, что запись была
  избыточной, а не просто шумной.
- Замечаний линтера: 673 → 514 на момент записи, работа продолжается.

### 8.6. Заявленное время старта CLI недостижимо в принципе

Замер 2026-08-04: `xec --help` — **400–520 мс** при заявленных в CLAUDE.md
«<50 ms required, <30 ms target».

Существенно: пустой `node -e ""` на той же машине стоит **~45 мс**. То есть
цель <50 мс недостижима любым Node-CLI ещё до выполнения хоть одной строки
нашего кода — это не невыполненная цель, а невозможная.

Причина основной части накладных расходов найдена: `apps/xec/src/main.ts`
статически импортирует `@xec-sh/ops` (`TaskManager`, `ConfigurationManager`,
`executeDirectCommand`), а это тянет всю конфиг- и секрет-машинерию на ~15 000
строк — ради вывода справки.

Заявления в CLAUDE.md исправлены на измеримые (<150 мс) с указанием причины.
Сам ленивый импорт `ops` — отдельная задача этапа B.

### 8.7. Потеря всего вывода больше 64 КБ (критично, исправлено)

Худший дефект из найденных за обе итерации. Собирающий `Transform` писал в
собственную readable-сторону, которую никто не читал. Как только её буфер
заполнялся, обратное давление запирало stdout дочернего процесса в 64-килобайтном
канале ОС — и всё вставало.

Замер до исправления:

| Объём | Получено | Код выхода |
|---|---|---|
| 60 КБ | 60 000 байт | 0 |
| 64 КБ | 65 536 байт | 0 |
| **70 КБ** | **0 байт** | **0** |
| 100 КБ | 0 байт | 0 |
| 200 КБ | — | **зависание навсегда** |

То есть команда, выдавшая чуть больше 64 КБ, возвращала **пустой stdout с кодом
успеха**. Это задевает всё реальное: чтение файла, `kubectl get -o json`,
`docker logs`, подробная сборка. Шаг CI, чей вывод перевалил за 64 КБ,
рапортовал успех с пустым результатом.

После: 5 МБ возвращаются целиком за 145 мс — на local, SSH и Docker одинаково;
stdout и stderr остаются раздельными по 200 КБ каждый.

### 8.8. Процесс, убитый сигналом, считался успешным (исправлено)

Node сообщает `code: null, signal: 'SIGKILL'`, а null сводился к нулю.
Воспроизведено: `kill -KILL $$` → `exitCode: 0, ok: true`. Убийство по OOM или
остановка пода оркестратором были неотличимы от чистого прогона — CI счёл бы
убитый деплой зелёным.

Теперь `ok` ложен при любом сигнале, а код выхода следует соглашению оболочек
`128 + номер сигнала`: SIGKILL → 137, SIGTERM → 143.

### 8.9. Секреты в событиях адаптеров (исправлено)

События уровня движка маскировались, события адаптеров — нет. То есть
`ssh:execute`, `docker:exec`, `k8s:exec` и `command:retry` публиковали сырую
команду. Подписываются на них ровно ради логов и аудита — то есть секрет уходил
в тот сток, которому интегратор доверяет больше всего. Воспроизведено вживую.

### 8.10. Обход проверки целостности через HTTP-редирект (исправлено)

Проверялся только первый URL, поэтому разрешённый CDN, перенаправляющий в другое
место, доставлял код с запрещённого хоста — а lockfile закреплял его под
разрешённым URL, легализуя подмену. Теперь редиректы обрабатываются вручную с
проверкой хоста на каждом переходе.

### 8.11. Маскирование расширено, но осознанно неполно

Добавлено покрытие десяти видов секретов: учётные данные в URL
(postgres/redis/mongodb), токены Google, Slack, Stripe, GitLab, npm,
идентификаторы ключей AWS, basic-auth в командной строке, PEM-ключи любых
алгоритмов.

**Сознательно не покрыт** голый 40-символьный секрет AWS: паттерн, достаточно
широкий, чтобы его поймать, вычищает и все git-хеши из вывода — проверено. Молча
портить настоящий вывод хуже, чем пропустить ключ, встречающийся вовсе без
контекста; будучи присвоенным переменной или вставленным в URL, он ловится.

## 9. Третий проход: что нашлось при доведении линтера до нуля

Требование «ни одного предупреждения от компилятора и от линтера» оказалось не
косметической задачей. Проходя по 511 замечаниям, я нашёл дефекты, которые
никакой обзор кода не показал бы, потому что каждый из них выглядел как
работающий код.

### 9.1. Маскирование секретов было квадратичным (критично, исправлено)

Каждый результат — stdout, stderr и строка команды — проходит через набор
паттернов, поэтому их стоимость есть стоимость каждой команды. Два паттерна
откатывались квадратично:

- правило URL-учёток было привязано к `[a-z]`, что давало движку кандидата на
  старт в каждой букве, а жадный разбор схемы уходил до конца ввода и обратно.
  **200 КБ обычного вывода стоили 29 секунд.**
- правила PEM сканировали до конца ввода от каждого `-----BEGIN` без пары.
  **800 КБ вывода, похожего на ключи, стоили 6,8 секунды.**

Именно это выглядело как зависание `$` на выводе больше ~128 КБ: команды не
были заблокированы — они всё ещё маскировались. После привязки к литералу
`://` и запрета `-----BEGIN` внутри тела PEM 1 МБ маскируется за ~8 мс.
`test/unit/utils/masking-cost.test.ts` фиксирует стоимость на девяти формах
ввода, подобранных против стартового поиска каждого паттерна.

### 9.2. Каждая упавшая команда порождала необработанное отклонение (критично, исправлено)

Учёт активных процессов снимался через `executionPromise.finally(...)`.
`.finally()` возвращает **второй** промис, который отклоняется с той же причиной
и который никто не обрабатывает. Любая упавшая команда давала два отклонения:
пойманное вызывающим и ушедшее в `unhandledRejection` хоста. Для приложения,
которое считает их фатальными — а это поведение Node по умолчанию с v15, —
пойманный и обработанный сбой команды убивал процесс.

### 9.3. Объявленные и молча выброшенные опции (исправлено)

- `QuestionOptions.mask` печатал секрет открытым текстом — ровно тот отказ,
  ради предотвращения которого опция существует, и хуже тем, что выглядел
  работающим.
- `QuestionOptions.multiline` возвращал только первую строку.
- `SCRYPT_OPTIONS` и `TAG_LENGTH` в криптографии секретов не применялись:
  `promisify` разрешается в трёхаргументную перегрузку `scrypt`, поэтому
  параметры стоимости молча падали на умолчания Node. GCM также принимает
  усечённый тег, который пропорционально легче подделать.

### 9.4. Молчаливые отказы в switch (исправлено)

- **retry**: неизвестная стратегия оставляла задержку `undefined` → `NaN` →
  каждая повторная попытка срабатывала мгновенно.
- **deploy**: неизвестная стратегия не разворачивала ничего, а
  `results.every()` по пустому массиву рапортовал **успех**.
- **completion**: неподдерживаемая оболочка возвращала `undefined`, который
  затем записывался в файл скрипта дополнения.

### 9.5. Пятая площадка небезопасного имени файла (исправлено)

`teamKeyFileName()` санирует адрес участника, но `rotateMasterKey()` всё ещё
собирал путь из сырого `userId.replace('@','_at_')` — пропущено при первом
проходе, потому что ключом там служит `userId`, а не `email`.

### 9.6. Подсказки об ошибках были написаны и никогда не вызывались (исправлено)

`getValidationSuggestion()` и `getSystemErrorSuggestion()` дают точный совет
для отсутствующего файла, отказа в правах, отклонённого соединения, занятого
порта — и их не вызывал никто. `enhanceError()` распознаёт только ошибки
команды, соединения и таймаута, поэтому всё остальное доходило до пользователя
как «An unexpected error occurred». Тест, который бы это поймал, стоял с
`it.skip`, потому что утверждать было нечего.

### 9.7. Утечка движка на каждый `TargetApi.create()` (исправлено)

Движок создавался, чтобы доказать конструируемость цели, и выбрасывался без
`dispose()` — вместе с адаптером и его пулом соединений.

### 9.8. Осознанные послабления конфигурации

Где правило не окупается в конкретном контексте, оно ограничено по области с
причиной прямо в конфиге, а не обойдено: примеры — это документация, поэтому
показанная, но не вызванная функция там и есть смысл файла; тесты по построению
переопределяют `result` в каждом `it()`; `` $`cmd` `` — это вызов, о чём говорит
собственная опция `allowTaggedTemplates`; терминальные проверки сопоставляют
ANSI-последовательности, которые по определению управляющие символы. Фикстуры
выведены из проверки целиком — часть из них намеренно невалидна, и «починка»
уничтожила бы то, что они проверяют. **Каждый случай затенения импортированного
модуля исправлен, а не заглушен.**

### 9.9. Цена механической правки

Автоматическое удаление «неиспользуемых» переменных сломало 16 файлов: где
объявление убиралось, а присваивание оставалось (ReferenceError до первой
проверки), и где чтение геттера — `engine.parallel` — и было тем, что создаёт
объект. Типизация поймала только часть, потому что tsconfig ряда пакетов не
покрывает тесты. Вывод для будущих проходов: обращение к свойству не является
чистым выражением, и после любой механической правки нужен полный прогон
тестов, а не только `tsc`.

## 10. Четвёртый проход: DX-аудит — интуитивность API против его обещаний (2026-08-04)

Метод: не чтение кода, а практика — типовые сценарии пользователя выполнены на
живом API и сверены с эталонами эргономики (zx, execa, dax, Bun Shell). Затем
каждый разрыв закрыт и закреплён тестом.

### 10.1. Флагманский синтаксис падал на одном из четырёх окружений (критично, исправлено)

`$.k8s(target)`cmd`` бросал `engine.run is not a function`: callable-прокси
оборачивал K8sExecutionContext как ExecutionEngine. Контекст не имел ни `cd`,
ни `env`, ни `timeout`. Через это же были сломаны потребители в ops:
`xec in pod --cwd ...` падал на `engine.cd is not a function`. Теперь все
четыре окружения дают одну chain-поверхность (закреплено
`environment-uniformity.test.ts`), k8s-контекст строится по образцу ssh.

### 10.2. Опции, принимаемые и применяемые не там (критично, исправлено)

- **Docker игнорировал `command.cwd`** — `.cd('/app')` менял каталог локального
  docker CLI (ENOENT, если путь контейнера не существует локально). Теперь
  транслируется в `exec/run -w`.
- **K8s применял `cwd`/`env` к локальному процессу kubectl** — `.env({TOKEN})`
  экспортировал секрет в окружение оператора, под его не видел. Теперь оба
  уезжают в под shell-прелюдией (`cd … && export …`), имена валидируются,
  значения квотируются; локальный kubectl получает только окружение оператора.
- **Корень**: BaseAdapter подставлял `process.cwd()` как амбиентный `defaultCwd`
  каждой команде. SSH-адаптер носил обходной костыль, вырезавший его обратно —
  заодно уничтожая и явно настроенный `defaultCwd`. Амбиентный default удалён.
- **AbortSignal** уважал только local; теперь ssh (сигнал в канал), docker и
  k8s (kill CLI-процесса) — с отсоединением слушателя на всех путях завершения.
- **SSH молча терял Readable stdin** — exec-слой всегда умел стримы, адаптер
  возвращал undefined.

### 10.3. Переполнение maxBuffer было потерей данных в форме успеха (критично, исправлено)

10 КБ вывода при лимите 1 КБ: пустой stdout, exit 0, `ok: true` — даже в
throw-режиме. Собирающий Transform ошибался, вытирал буфер, а адаптер не
слушал его ошибок. Теперь: усечение по лимиту, kill производителя (как в
Node `exec` и execa), громкий `MaxBufferExceededError` с сохранённой головой;
в nothrow — `ok:false` с головой в stdout. На всех четырёх адаптерах.

### 10.4. Эргономика результата (исправлено)

- `${result}` давал `[object Object]`; теперь — stdout без завершающего
  перевода строки, модель `$(...)` шелла. `valueOf()` — trim.
- Сообщение CommandError не содержало stderr — «exit code 1» без причины;
  теперь включает голову stderr (уже замаскированную).
- `verbose` был объявлен в конфиге и не использовался нигде; теперь эхо
  команд в stderr с редакцией секретов, и `$.verbose = true` работает
  (set-ловушка вместо тихого присваивания на прокси).
- `$.docker('container')` был задокументирован в README и падал с TypeError;
  теперь работает, симметрично `$.ssh('user@host')` и `$.k8s('ns/pod')`.
- Из публичных типов убраны `any`: `cache(CacheOptions)`, `child:
  ChildProcess`, `retry(RetryOptions)`.

### 10.5. Сопутствующее

`handleTimeout` в base-adapter снимал таймер через `promise.finally()` — тот же
класс двойного отклонения, что был в process-context: каждая падающая команда
дополнительно давала unhandledRejection. Исправлено на `then(clear, clear)`.

### 10.6. Позиционирование

README (корневой и npm-овский @xec-sh/core) переписаны вокруг «проблемы шва»
из STRATEGY.md: одна `$` через четыре окружения — и раздел «Контракт», каждое
утверждение которого существует в репозитории как тест. Убрано ложное «Zero
external runtime dependencies» (реально: ssh2, js-yaml, zod).

## 11. Прямое сравнение с zx 8.9.0 (2026-08-04)

Метод: прочитан исходник `experiments/zx` (src/core.ts — 1105 строк, util.ts,
error.ts, плюс вендорённый движок `zurk/spawn` из собранного бандла), затем
каждое расхождение проверено измерением, а не рассуждением.

### 11.1. Гипотезы, которые НЕ подтвердились

Отмечаю первыми, потому что на них было бы легко построить ложное
преимущество:

- **«quoting у zx привязан к bash и ломается в dash/alpine»** — неверно.
  `$'...'` (ANSI-C quoting) поддерживают и busybox sh, и современный dash.
  Проверено запуском в `alpine:3.18`: обе схемы дают одинаковый результат.
- **«префикс `set -euo pipefail` не работает в busybox»** — неверно, busybox
  поддерживает `pipefail`. Проверено там же.

Наше преимущество в этой области сводится к другому: диалект выбирается
автоматически по целевой оболочке (`posix`/`cmd`/`powershell`), тогда как в
zx переключение ручное (`usePwsh()`), и `$.quote` — глобальная мутируемая
переменная.

### 11.2. Что перенято и закрыто в этом проходе

| Возможность | zx | было у нас | стало |
|---|---|---|---|
| Живой доступ к процессу (`child`, `pid`, `stdin`) | ✅ геттеры | ❌ **константы `undefined`/`null`** | ✅ `ProcessHandle` во всех окружениях |
| Kill убивает дерево процессов | ✅ (`@webpod/ps` + группы) | ❌ только abort | ✅ группы + `ps`-обход, без зависимостей |
| `stdall` — порядок вывода | ✅ | ❌ | ✅ общий сток на оба потока |
| Расшифровка кода выхода | ✅ таблица из 30 | ❌ | ✅ 10 кодов, которые меняют решение |
| Duration-строки (`'30s'`) | ✅ | ❌ только мс | ✅ обе формы |
| stderr в сообщении ошибки | ✅ | ❌ | ✅ голова stderr |
| `$.verbose` | ✅ | ❌ объявлен и мёртв | ✅ с редакцией секретов |
| `${result}` → stdout | ✅ | ❌ `[object Object]` | ✅ |

### 11.3. Где мы принципиально впереди

**Область применения.** zx заканчивается на локальной машине. Тот же `$` у нас
работает по SSH, в контейнере и в поде — это и есть причина существования
проекта.

**Границы памяти (измерено).** У zx нет `maxBuffer` вовсе: вывод копится в
неограниченном массиве. Команда, отдавшая 300 МБ, увеличила RSS процесса на
**299 МБ** — на большем объёме это OOM всего приложения. У нас — лимит,
убийство производителя и громкий отказ с сохранённой головой вывода. Для
инструмента, исполняющего команды на инфраструктуре, это разница между
«лог оказался больше ожидаемого» и «упал оркестратор».

**Маскирование секретов.** В zx его нет ни в одном слое. У нас — в выводе,
событиях, сообщениях об ошибках и в эхо `verbose`, одним набором правил.

**Поверхность зависимостей.** У zx в `package.json` пусто, но это не «ноль
зависимостей»: сборка **инлайнит 30 сторонних пакетов** (chalk, which,
@webpod/ps, zurk, fast-glob, globby, yaml, minimist, dotenv, fs-extra и др.,
748 КБ в `vendor-extra.cjs`). Инлайненный код не виден ни `npm audit`, ни
SCA-инструментам — для аудита это хуже, чем объявленная зависимость. У нас
после этого прохода: **одна** объявленная зависимость (`ssh2`), загружаемая
лениво; локальное исполнение подтверждённо грузит **ноль** внешних модулей
(измерено на собранном `dist` чистым node).

**Единообразие handle.** У zx `child` — это `ChildProcess`, что честно только
локально. Наш `ProcessHandle` одинаков для четырёх окружений и не притворяется:
у SSH нет `pid`, потому что удалённый pid отсюда не узнать, а отдать локальный
означало бы пригласить послать сигнал не на ту машину.

### 11.4. Где zx впереди, и что с этим делать

- ~~**Caller location в ошибке**~~ — закрыто. Цена измерена: захват стека без
  форматирования — 1.4 мкс на команду (форматирование только при падении),
  против спавна процесса в миллисекунды это ~0.03%. Отключается флагом
  `captureCallSite: false`.

  Побочная находка при написании теста на это: **`.catch()` на упавшей
  команде молча не срабатывал.** Ветка, решающая, отклонять ли промис при
  ненулевом коде, проверяла «передан ли onfulfilled?». `.catch(fn)` и
  `.then(null, fn)` приходят без него — обе уходили в неотклоняющую ветку,
  команда резолвилась своим результатом, обработчик не вызывался. Стандартная
  идиома промисов сообщала об успехе для упавшей команды. Исправлено.
- **Синхронный режим** (`$.sync`), REPL и markdown-скрипты. Сознательно вне
  области: `$.sync` несовместим с SSH/Docker/K8s, а markdown-исполнение
  относится к `@xec-sh/loader`.
- **`$({halt: true})`** — отложенный запуск. У нас исполнение и так ленивое,
  плюс появился явный `.start()`.

### 11.5. Сознательные расхождения

- **Конфигурация через переменные окружения.** zx читает `ZX_*` и позволяет
  так подменить в том числе `shell`. Для инструмента, исполняющего команды на
  проде, это вектор: переменная окружения в CI меняет интерпретатор всех
  команд. Мы этого не делаем и не будем.
- **Конфигурация после старта.** У zx методы мутируют снапшот на месте. У нас
  каждый шаг цепочки возвращает новую команду, а попытка настроить уже
  запущенную теперь падает — иначе `p.start().signal(ac)` молча отменял бы
  ничто.

### 11.6. Побочные находки прохода

Работа по zx вскрыла два дефекта, к самому сравнению отношения не имеющих:

- **`.catch()` на упавшей команде молча не срабатывал** (§11.4).
- **`process.cwd()` как амбиентный cwd в ops.** Тот же класс, что был убран из
  BaseAdapter в §10.2, но уровнем выше: `executeStepCommand` подставлял
  `process.cwd()` любой цели. Пока Docker и K8s игнорировали cwd, это было
  безвредно; как только они стали его уважать, каждая контейнерная задача
  превращалась в `docker exec -w /Users/<оператор>/<проект>` и падала с кодом
  127. Урок повторный: **амбиентное значение по умолчанию, осмысленное только
  локально, — это дефект в системе, которая исполняет команды не только
  локально.** Теперь cwd применяется, только если его запросили.

Отдельно: тесты `watch` на этой машине падают из-за зависшего `fseventsd`
(голый `fs.watch` в чистом Node не доставляет события) — см. память проекта,
не код. Тест `docker image pull` падает из-за недоступности Docker Hub.
